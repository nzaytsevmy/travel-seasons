# Визуальный выпуск TravelTribe

Цель — доказать, что изменённый интерфейс понятен, устойчив и работает на живой
странице, а не только собирается.

## Источники истины

Перед работой прочитай [`CLAUDE.md`](../../../CLAUDE.md), особенно разделы
«Design canon», «Сетка и адаптив» и обязательный гейт. Для денежных элементов
также прочитай [`MONETIZATION-2026.md`](../../../MONETIZATION-2026.md).

Не копируй их требования сюда и не ослабляй пороги. При расхождении прав
актуальный файл репозитория.

## Рабочий процесс

1. Определи изменённые типы страниц, компоненты, состояния и денежные пути.
   Перед исправлением бага получи воспроизводимое RED-доказательство.
2. Осмотри существующий дизайн и живые канарейки этого типа. Продолжай язык
   TravelTribe; не вводи новый визуальный паттерн без продуктовой причины.
3. Реализуй минимальное изменение. Сохрани семантическую структуру, keyboard
   navigation, focus, reduced motion, контраст и touch target не меньше 44 px.
4. Проверь браузером после выполнения JS:
   - 402 px и 1280 px для каждого изменённого типа;
   - 768 px, если затронуты сетка, навигация или брейкпоинт;
   - прицельный viewport изменённого блока и состояния, а не только full-page.
5. Проверь текст, изображения, overflow, sticky/fixed элементы, таблицы, формы,
   внешние переходы и CTA. Для денежного пути пройди клик до корректного
   партнёрского URL, не совершая покупку.
6. Запусти пропорциональный гейт:
   - всегда `npm run build` и `npm run check:seo`;
   - релевантные Playwright-тесты для локального изменения;
   - полный `npx playwright test` для кода, CSS, layout или общего компонента;
   - Lighthouse для изменённых типов согласно `CLAUDE.md`.
7. При падении на нетронутой странице сначала докажи pre-existing через A/B на
   чистом `main`. Не двигай threshold и не обновляй snapshots до ручной
   визуальной проверки.
8. Если пользователь просил реализацию, дождись полного CI, merge и deploy,
   затем проверь live URL и ключевой сценарий. Для ревью без запроса на правку
   ничего не публикуй.

## Результат

Сообщи сначала пользовательский результат. Приложи проверенные размеры и
состояния, команды/CI, live-проверку и оставшиеся ограничения. `Build green`
не называй доказательством корректного дизайна.

При изменении skill используй кейсы из
[`references/evaluation-cases.json`](references/evaluation-cases.json); в
обычной дизайн-задаче их не загружай.
